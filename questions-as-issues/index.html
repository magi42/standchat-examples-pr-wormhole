    How it works

    Let visitors file their objections as issues

    People weighing a switch have specific doubts, and a chat bubble in the corner rarely draws them out. Here each doubt becomes an issue in a working mini tracker, in the product’s own idiom. Stand’s AI Stand-in picks it up, answers in the issue’s activity feed and links the team’s answered issues. A person from your team can join at any point, and every question reaches them with its issue ID, priority and label.

    There’s no stand.js on this page. The tracker is plain JavaScript in this folder, with no dependencies, talking to Stand’s Visitor API over HTTP and a WebSocket.

    Try it

    1. Press C anywhere, or click File a question. Give the issue a title, a priority (“How much does this block your switch?”) and a label, then press ⌘ ↵ (Ctrl ↵ on Windows and Linux).
    2. Watch it land in Triage, get picked up, move to In Progress while the answer is written, and to In Review when it arrives.
    3. Hover or click an issue mention in the answer, like SW-3. It opens one of Axial’s answered issues, with a way back.
    4. Comment on your issue, file a second one, then reload the page. Everything comes back where it was.
    5. Stay on the keyboard: J and K move, S, P and L change the issue you’re on, and ⌘ K does the rest, including End conversation. On a phone, the New issue button and the sheets do the same.
    Chats here use site: 'demo', Stand Chat’s shared demo site, which works on any domain. Its demo Stand-in follows this page’s prompt and speaks for the made-up tracker. With your own Site ID, your own Stand-ins answer, and your team can take over any issue from Stand.

    1. One conversation, many issues

    Every issue is a thread inside a single Stand conversation. A session per issue would count each question as a separate chat against your plan, and scatter one visit across many transcripts. Instead, every visitor message starts with its issue’s ID. The first message of an issue also carries its priority and labels:

    SW-9 [High · Migration]: Can we keep our old issue keys?

Our docs and commits link to keys like OPS-1423.

SW-9: And how long does the import itself take?

SW-10 [No priority · Pricing]: Is SSO included in Standard?

    Replies belong to the issue of the latest visitor message before them. model.js reads everything back from the transcript, so a reload rebuilds the same issues without storing them anywhere:

    // "SW-12 [High · Migration]: " files an issue; "SW-12: " comments on it.
export function newIssueMessage({ id, title, description, priority, labels }) {
  const meta = [priorityName(priority), labels.map(labelName).join(', ')]
    .filter(Boolean).join(' · ');
  const head = `${id} [${meta}]: ${title}`;
  return description ? `${head}\n\n${description}` : head;
}

// Reading it back: a reply belongs to the issue asked about just before it.
let thread = null;
for (const m of state.messages) {
  if (m.senderType === 'visitor') {
    // { id, kind: 'issue' | 'comment', title, priority, labels, … }
    const parsed = parseVisitorText(m.body);
    // The first message with an ID files that issue; later ones comment.
    thread = open(parsed.id, m, parsed);
  } else if (thread && isConversation(m)) {
    thread.items.push(comment(m, replyAuthor(m, hostAt(m.seq)), m.body));
  }
}

    While an answer is on its way, the other issues wait. Their comment boxes say which issue is being answered, and nothing is queued. A teammate may still answer out of order, and that’s fine.

    2. The issue lifecycle is the conversation’s lifecycle

    No status is made up. Each one comes from the transcript and the client’s state:

    StatusWhen
    TriageThe issue’s first message is on its way. The very first one also creates the conversation.
    In ProgressAn answer is due: the last message on the issue is the visitor’s. The icon spins while the Stand-in is writing.
    In ReviewThe answer landed. The issue says “Waiting on you”.
    DoneThe visitor marked it done. That stays on the page, until they comment again.
    CanceledThe conversation ended before the issue got an answer. Answered issues close as Done.

    The assignee is whoever Stand says is answering. When a person joins, a handoff card arrives, the feed says “Maya joined · assigned”, and every open issue moves to her. The tracker only sets the pace: a new issue stays in Triage for a moment before the pickup, and the typing indicator shows briefly before the answer lands, so every step can be seen.

    3. Answers that point at issues

    The prompt lists Axial’s answered issues and plans, each next to the facts it holds. When one of them answers the question, the Stand-in writes its name in double square brackets. The tracker turns that into an issue mention, with its status, ID and title and a preview on hover. A plan becomes a chip that scrolls to the pricing table.

    Past sprints import with their scope and dates, so your velocity charts keep their history [[SW-3]].
    // [[SW-3]] names an issue and [[Plan: Plus]] a plan. Anything else stays plain text.
export function resolveRef(raw) {
  const name = raw.toLowerCase().replace(/\s+/g, ' ').trim().replace(/[.,;:!?]+$/, '');
  const issue = /^sw-(\d{1,6})\b/.exec(name);
  if (issue) return { kind: 'issue', id: `SW-${Number(issue[1])}` };
  const plan = /^(?:(?:plan|pricing)\s*[:›>-]?\s*)?([a-z]+)(?:\s+plan)?$/.exec(name);
  if (plan && PLAN_IDS.includes(plan[1])) return { kind: 'plan', id: plan[1] };
  return null;
}

    A bare ID like SW-6 in a reply becomes a mention too, the way a tracker links them. References only ever navigate. Replies are never treated as HTML: they’re split into text nodes, with a small safe subset for paragraphs, lists, bold, code and links.

    4. The prompt

    The first message creates the conversation and carries this private context, at most 2,000 characters. Its facts match the page and Axial’s answered issues, so the Stand-in and the FAQ agree. The last line says where the first issue was filed. Later context can’t change it, which is why every message carries its own ID, priority and labels.

    You are answering visitors on the website of Axial, a fictional issue tracker for software teams (a demo page on examples.stand.chat; Axial is invented). Speak as Axial's team. Keep replies short: 1-3 sentences unless asked for detail. If a fact isn't below, say you're not sure and offer to bring in someone from the team. Don't invent prices, limits or features.

How this page works: visitors file questions as issues. Every visitor message starts with an issue ID and a colon. A new issue: "SW-12 [High · Migration]: title", maybe with a description below. A comment on it: "SW-12: text". Answer about that issue. Don't repeat the ID prefix.

Facts. Link the issue or plan that holds the answer by writing its name in double square brackets, exactly as below, at most two per reply:
[[SW-1]] Import: issues, comments, attachments, status history, sprints and links, with original authors and dates, by CSV or API from legacy trackers. 40k issues in under an hour. Free dry runs.
[[SW-2]] Custom fields: select fields become labels; text, number and date fields become properties.
[[SW-3]] Sprint reports: past sprints import, so velocity charts keep your history. Story points become estimates.
[[SW-4]] SSO: SAML SSO on Plus, SCIM on Enterprise.
[[SW-5]] Timeline: 1-2 week pilot with one team, the rest in 2-6 weeks.
[[SW-6]] Both tools at once: two-way sync (Plus and up) keeps them in step for up to 90 days.
[[SW-7]] Data: US or EU (Frankfurt), per workspace. SOC 2 Type II.
[[SW-8]] API: GraphQL and webhooks. Old issue keys keep working.

    5. What your team reads

    In Stand, the conversation reads like a triage queue: each question arrives with its issue ID, its priority and its label, in the visitor’s own words. That’s the product learning. You see which doubts come up, and how much each one blocks a switch. This is the conversation on this page so far, exactly as Stand stores it:

    

      
    The files
    
      
      
        
    • stand-visitor.js is the network side: discovery, one-time creation, sends, the WebSocket, recovery, handoffs and follow-ups, with no DOM. It’s the client from the Stand Inline example, with this folder’s own storage keys.
      • 
        
    • model.js turns the transcript into issues: threads, statuses, assignees and activity, plus the message format and the reference parser. No DOM, no network.
      • 
        
    • tracker.js and overlays.js draw the tracker: the list, the issue view, the New issue dialog, menus, the command menu and toasts. tracker.css styles them.
      • 
        
    • app.js connects the pieces, keeps what the transcript can’t know in sessionStorage, and owns the keyboard.
      • 
        
    • prompt.js and seed.js hold the prompt and Axial’s answered issues. page.js and style.css are the made-up company’s site.
      • 
      
    

      
    Good to know
    
      
      
        
    • Honest about AI. The assignee is whoever Stand says is answering, by the name Stand gives, with an AI chip for a Stand-in. Axial’s answered issues are signed by its (fictional) team; live answers never are.
      • 
        
    • Closing isn’t ending. Closing an issue or a dialog keeps the conversation going. Only End conversation, in an issue’s menu or ⌘ K, ends it in Stand. The issues stay in the list, closed, and Start a new conversation picks up the numbering where it left off.
      • 
        
    • A reload keeps everything. The client restores the transcript. The page itself stores only what the transcript can’t tell: Done marks, what was read, drafts, the open issue, and the issues of a conversation that ended.
      • 
        
    • Nobody around. If discovery finds nobody to answer, the tracker says so and offers to try again, and the answered issues stay browsable. A comment that fails to send stays in place as “Not delivered”, with a Retry that reuses its message ID. An uncertain first send is never retried on its own.
      • 
        
    • Priority and labels travel once. They go with an issue’s first message, so your team sees them. Changes made later stay on this page.
      • 
        
    • Keyboard, touch and screen readers. Every shortcut has a click or a tap. The list is a listbox, focus returns where it came from, and whole replies are announced in a live region. On phones, a New issue button replaces C and issues open as full-screen sheets.
      • 
        
    • Reduced motion. The tilt, the gliding rows and the spinning status icons stop. The states stay.
      • 
        
    • It’s a beta. The Visitor API can grow new fields and events. The client ignores what it doesn’t know.

A separate Claude agent built the page in its own git worktree: it studied a well-known issue tracker’s site for tone and rhythm, tuned the prompt in real conversations with Stand’s demo Stand-in, drove the rare states (handoffs, follow-up offers, failed sends) through a fake backend, and checked its own screenshots in headless Chrome at desktop and phone sizes.
    

          
    The prompt, lightly edited
    
          
    Given Stand Chat's target audience, find ten products they look up to and would recognize, products that might have the same problems as their own. It could be the market's dominant player. For each, work out how it could embed Stand on its website in an innovative way that pulls visitors in to interact. Not just a chat button, but something novel: something our audience would see and think, "I want that on MY website."

Build each one in a separate session, as its own pull request. Don't use the brand names, but make each website resemble its product in a subtle way.

    This example’s brief
    
          
    A keyboard-first issue tracker’s “Switching” page, where visitors’ questions become issues in a live mini tracker. The conversation’s lifecycle is the issue’s: C opens a composer with a priority (“How much does this block your switch?”) and labels, the issue lands in Triage, the Stand-in picks it up and it moves to In Progress, the answer arrives as a comment, and it waits In Review.

Several issues are threads over one Stand session, with prefixes like “SW-12 [High · Migration]:” that parse back after a reload. Eight answered questions from the invented company’s team make the first view feel alive and are targets for [[SW-3]] mentions.
