    Airstrip is a fictional company. This page demonstrates a custom chat UI on Stand Chat’s Visitor API.

    How it works

    Let visitors bring their own input, and talk about their result

    The first question on a hosting site is “will it work with my project?” This page answers it with the visitor’s own package.json: read in the browser, played back as a deployment, and open to questions about every finding and log line. The conversation runs on Stand’s Visitor API, and whoever answers already knows the visitor’s stack, because the first question carries a summary of it.

    Try it

    1. Watch the sample deploy. Then drop your own package.json onto the page, paste it anywhere with ⌘V or Ctrl+V, or pick another sample. The tricky one fails.
    2. Click Ask on a finding, or point at a log line and click its Ask. The conversation opens beside the deployment, on that finding’s thread, with questions to start from.
    3. In the answer, click a highlighted name like bcrypt or Building. The page scrolls to that finding or build phase and lights up its log lines.
    4. Ask about something else: it gets its own thread in the same conversation. Reload, and your package.json, the log and every thread come back.
    Chats here use site: 'demo', Stand Chat’s shared demo site, which answers on any domain. Its demo Stand-in follows this page’s prompt and speaks for the made-up company. With your own Site ID, your own Stand-ins and your team answer, and every conversation lands in Stand.

    1. Read the input in the browser

    The package.json never leaves the page. It’s parsed with JSON.parse, checked by a rules engine, and turned into a deployment that only exists as data. Nothing reaches Stand until the visitor sends a question, and then only the question and a summary of the stack.

    const { pkg, invalid } = readPackageJson(await file.text()); // Strict JSON, like npm
const analysis = analyze(pkg, { invalid }); // The rules engine: findings, framework, output
const deployment = simulate(analysis, { region, key: text }); // The log, seeded by the input

    A near-miss still gets analyzed. Comments or a trailing comma make npm fail, so the page reads the file leniently, and the first finding says why the real install would stop.

    2. A rules engine you can read

    analyze.js holds 40 rules about the made-up platform: the framework and its output, the Node range in engines, the package manager, native addons, headless browsers, WebSocket servers, background jobs, ORMs, uploads, auth on preview URLs, monorepo roots and more. Each finding carries what the page and the conversation need.

    if (has('puppeteer')) {
  add({
    id: 'puppeteer', // Also the name answers point with: [[puppeteer]]
    level: 'error', // ok, info, warn or error
    title: 'puppeteer is too big for a function',
    summary: 'Its Chromium pushes the function past the 200 MB limit.',
    brief: 'bundled Chromium exceeds the 200 MB function limit', // For the prompt
    fatal: 'Deploying', // The simulated deployment fails here
    log: {
      phase: 'Installing', level: 'warn',
      text: 'puppeteer@23.11.1: downloading Chromium (171 MB)',
    },
    questions: ['How do I run a headless browser on Airstrip?'],
  });
}

    The build log in deploy.js is generated from the findings and seeded by the input, so the same package.json always gives the same lines. That matters for the conversation: a thread about a log line finds its line again after a reload.

    3. The stack rides along with the first question

    The first question creates the Stand session, with a private prompt of up to 2,000 characters: who answers, the platform’s facts, the page’s conventions, and a summary of this stack. The summary fills up most important first, as far as it fits: every warning, then their reasons, tips, up to 25 package names and what works as is.     4. One conversation, a thread per finding

    Every finding, log line and phase can start a thread, and they all share one Stand conversation, so the site owner is charged for one chat, not twenty. Each question starts with its subject. The team sees exactly what was asked about, and the panel sorts messages into threads by reading the subjects back, even after a reload.

    [Finding: bcrypt] Will this still work if I move login to the edge?
[Log: Installing "puppeteer@23.11.1: downloading Chromium (171 MB)"] Why is this so big?
[Stack] Can I run this on the free plan?
    export function parseMessage(body) {
  const m = body.match(/^\[(Finding|Log|Stack)(?::\s*([^\]]*))?\]\s*/);
  // m[1] is the kind of subject; m[2] a finding id, or a phase and its log line.
  // The rest is the question, shown in its thread without the prefix.
}

    Replies belong to the thread of the latest question before them. While an answer is on its way, the panel asks the visitor to wait before starting a thread somewhere else. Later messages can’t change the prompt, so when the visitor loads another package.json mid-conversation, their next question carries it along as [New stack: …].

    5. Answers that point at the deployment

    The prompt lists the page’s vocabulary: this stack’s finding ids, the five build phases and the three plans, and asks for them in double square brackets. The panel turns names it recognizes into buttons that scroll to the finding, expand the phase or open the plan. Anything else stays plain text, and a reply is only ever escaped text with a small formatting subset.

    6. What your team learns

    In Stand, every conversation opens with the visitor’s stack, and every question names the finding or log line behind it. After a few weeks, that’s a map of which stacks bring people to your site and which findings stop them. If a third of the conversations start on the WebSockets finding, that’s a product decision, not a support queue.

    Good to know

    • Honest about AI. The panel names whoever answers exactly as Stand reports them, with an AI badge for a Stand-in. If someone from the team takes over, the badge changes and the conversation says so.
    • Closing isn’t ending. The × and Esc put the panel away; replies keep arriving. End conversation, in the panel’s menu, ends it in Stand.
    • A reload keeps everything. The client restores the transcript from sessionStorage and Stand, the threads come back from each message’s subject, and the package.json and its deployment (same lines, same times) are saved per tab.
    • Nobody around. The analysis works on its own. When Stand has nobody to answer, the Ask buttons open a panel that says so, with a way to check again.
    • Keyboard and screen readers. Every Ask is a button; in the build log, arrow keys move between lines and Enter asks about one. The transcript announces whole replies, not typing, and Esc closes the panel and returns focus.
    • Reduced motion. The deployment appears at once instead of streaming, and nothing slides or shimmers.
    • It’s a beta. The Visitor API can add fields and events. The client ignores what it doesn’t know, and the page still works as a static analyzer if the chat can’t load.

    This example’s brief

    "Will it deploy?" for a made-up frontend cloud in the black-and-white, grid-lined style of the platform many web developers deploy to. The visitor drops or pastes a package.json (or picks a sample), and the page runs a local, simulated deployment of their stack: a streaming build log with collapsible phases, a deployment card and a list of findings from a rules engine of 25 to 40 rules. Every finding and log line can be asked about. The conversation docks beside the deployment like an inspector, with chips for what it's about. The first message's prompt carries a compact stack summary; later questions carry their subject as a prefix, threading one Stand session. Answers reference findings and build phases by name, and those become chips that highlight the page. "Analyzed in your browser. Only what you ask about is sent, with a summary of your stack." Make it true.

    If you try this yourself

    • Start from the custom chat UI guide and the demo Site ID, so the agent can hold real conversations from localhost while it builds.
    • Budget the prompt. 2,000 characters go fast, so have the agent measure it for every sample, and fill it most important first: here, every warning, then their reasons, tips and package names.
    • Make the simulation deterministic. Seeding the log from the input means a reload regenerates the same lines, and threads anchored to a log line still find it.
    • Probe the reference convention before wiring the UI. Once the prompt listed the exact names, the demo Stand-in used them reliably; a closed vocabulary with plain-text fallback kept stray names harmless.
    • Probe for what it shouldn’t say, too. Pressed for “a product name”, the Stand-in recommended real companies until the prompt said never to, even when asked, and gave a generic example to use instead.
