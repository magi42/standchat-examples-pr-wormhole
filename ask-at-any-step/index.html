Sell Grow Stories Pricing How this page works

Awning is a fictional company, and so are its merchants. This page demonstrates a custom chat UI on Stand Chat’s Visitor API: the questions you ask in the wizard are real conversations.

How it works

Let people ask at the step where they hesitate

Signups, onboarding and quote forms lose people at the one step where their situation doesn’t fit the options. Here, every step of a store setup wizard has its own “Doesn’t fit? Ask us” field. The question goes to Stand with the step and every answer given so far, the reply appears inside that step, and it can move the wizard to the plan or checklist item it mentions.

There’s no stand.js on this page. The wizard, the preview and the advisor are plain JavaScript modules in this folder, talking to Stand’s Visitor API (beta) over HTTP and a WebSocket.

Try it

  1. Pick what you’d sell and click through a step or two. The store on the right builds itself: products, currency, a booking block, pickup badges.
  2. At any step, type a question into Doesn’t fit? Ask us. Try “Do I need VAT in Germany?” on Markets, or “Which plan if we’re four people?” on Size.
  3. The answer appears inside the step, from a real AI Stand-in. Chips in it, like Checklist: Taxes or Plan: Main Street, take you to that part of the wizard.
  4. Move on and ask again. Store advisor, top right, keeps the whole conversation with a badge for each step. Reload: your answers and the conversation come back.
This example uses site: 'demo', Stand Chat’s shared demo site, which works on any domain. Its demo Stand-in follows the prompt below and answers as Awning’s team, but Awning is made up. With your own Site ID, your own Stand-ins answer, and your team can step in.

1. A field in every step, not a bubble in the corner

The ask field sits at the foot of each step card, where the hesitation happens. It creates nothing until the visitor sends a question, and the wizard works exactly the same for people who never use it.

<form class="ask-form">
  <label for="ask-3">Doesn’t fit? Ask us</label>
  <textarea id="ask-3" rows="1"
    placeholder="Do I need to register for VAT in Germany?"></textarea>
  <button type="submit" aria-label="Send your question">…</button>
</form>

2. Every question carries its step and the answers so far

There’s one Stand conversation per visitor, however many steps they ask on. Each message starts with a short, readable prefix: the step, then the answers given so far. The Stand-in answers for that situation, your team reads the same line in Stand, and after a reload the page parses the prefix to put each question back in its step. The UI strips it and shows the answers as chips.

export function composeQuestion(stepN, answers, text) {
  const step = STEPS[stepN - 1];
  const fields = answerFields(answers).map((f) => ` · ${f}`).join('');
  return `[Step ${step.n} · ${step.name}${fields}] ${text.trim()}`;
}

// Replies belong to the latest question before them, so they land in its step.
for (const m of state.messages) {
  if (m.senderType === 'visitor') {
    current = { ...parseQuestion(m.body), replies: [] };
    exchanges.push(current);
  } else if (isConversation(m)) {
    current?.replies.push(m);
  }
}

While a reply is due, the other steps’ fields wait for it (“Waiting for the answer on Step 3”), so replies never land in the wrong step.


      
3. The first question brings a summary

      
The first send creates the conversation, with a private prompt for whoever answers: who Awning is, the facts the Stand-in may use (plans, fees, taxes, shipping), the message format, the names it can point at, and the answers at the moment of the first question. It’s at most 2,000 characters. Here’s the one your first question would send:

      

      
const body = composeQuestion(step, wizard.answers, text);
const first = state.phase === 'available'; // No conversation yet: this creates it.
await client.send(body, first
  ? { prompt: buildPrompt(wizard.answers, step), analyticsId: 'setup-wizard' }
  : {});


      
4. Answers that move the wizard

      
The prompt lists the wizard’s parts by name and asks the Stand-in to point at one in double square brackets when it helps. The page turns a name it knows into a chip: a step jumps there and keeps your answers, a plan opens the Plan step with that plan, a checklist item or an app opens in the checklist, added if your answers hadn’t called for it. Unknown names render as plain text, and a reply can only ever navigate.

      
export const REFERENCES = [
  { name: 'Step: Markets', kind: 'step', target: 3, aliases: ['markets'] },
  { name: 'Plan: Main Street', kind: 'plan', target: 'mainstreet' },
  { name: 'Checklist: Taxes', kind: 'checklist', target: 'taxes', aliases: ['vat'] },
  { name: 'App: Subscriptions', kind: 'app', target: 'subscriptions' },
  // …
];

// In a reply, [[Checklist: Taxes]] becomes a chip. It can only navigate.
const ref = findReference(name); // null for names it doesn't know: plain text
chip.addEventListener('click', () => wizard.reveal(ref));


      
5. What your team learns

      
In Stand, each conversation reads like a record of hesitation: which step, with which answers, prompted which question, and what answered it. Patterns show up fast. If people with customers in three countries keep asking about VAT on the Markets step, that step needs a sentence about VAT.

      
Visitor   [Step 3 · Markets · sells: physical, subscriptions · customers: FI (home), DE, US] Do I need to register for VAT in Germany?
AI        Not at first. Under €10,000 a year of sales to other EU countries you charge Finnish VAT; above that, German VAT through the One-Stop Shop. [[Checklist: Taxes]]
Visitor   [Step 4 · Size · … · size: €1k–10k/mo, 11–100 products, just me] Is Corner enough if I add a candle club later?


      
The files

      
    
        
  • stand-visitor.js is the network side, shared with Stand Inline: discovery, one-time creation, sends with retries, the WebSocket, recovery and handoffs. No DOM.
    • 
        
  • advisor.js is the conversation model: the prefix, the prompt, exchanges per step and the reference names. No DOM either.
    • 
        
  • ask.js renders it: the field and helper notes in each step, the Store advisor panel, and every state from “Sending…” to an ended conversation.
    • 
        
  • steps.js, wizard.js and storefront.js are the made-up product: the questions, the admin-style wizard and the live store preview. art.js draws the icons, flags, products and map.
    • 
      


      
Good to know

      
    
        
  • Honest about who answers. Every answer shows the responder’s name as Stand gives it, with an AI chip for a Stand-in. If someone from your team takes over, the chip changes and the step says so.
    • 
        
  • Asking is optional, creating is deliberate. Opening the page, focusing a field or opening the advisor starts nothing. The first question starts the conversation, once.
    • 
        
  • Closing isn’t ending. Moving between steps or closing the advisor leaves the conversation running. End conversation in the advisor ends it, and Start a new conversation begins the next.
    • 
        
  • A reload keeps everything. The client restores the conversation from sessionStorage and Stand; the wizard keeps its answers and step there too. Questions find their steps again by their prefix.
    • 
        
  • Nobody around? If discovery finds no one to answer, each ask field says so and offers a retry. The wizard keeps working.
    • 
        
  • Keyboard and screen readers. Options are real checkboxes and radios, each step moves focus to its question, Esc closes the advisor, and whole answers are announced with the step they belong to. With reduced motion, steps and the preview change without animating.
    • 
        
  • It’s a beta. The Visitor API can grow new fields and events. The client ignores what it doesn’t know, and the wizard never depends on the chat.

This example’s brief

          
A setup wizard you can talk to, for a made-up commerce platform in the style of the market leader for independent merchants: a bold black-and-white marketing site around an admin-style, card-based “Start your store” wizard.

Six steps: what you sell, where you sell today, where your customers are (flags and a small map), how big you are, a store name with a domain check, and a recommended plan with a setup checklist tailored to the answers. A live storefront preview builds itself beside it.

Every step has an inline “Doesn’t fit? Ask us” field. The answer appears inside the step, and the whole conversation stays in a slim advisor panel with a step badge on each question. Each message carries its step and the answers so far in a compact prefix; the first message’s prompt summarizes all answers. Replies can point at steps, plans, checklist items and apps, and those references act. The wizard never depends on the chat.


          
If you try this yourself

          
    
            
  • Give your agent the custom chat UI guide. It’s written as a contract for coding agents, recovery rules included.
    • 
            
  • Start on the demo Site ID, and have the agent probe the prompt in real conversations before it builds any UI. Here, three rounds settled the facts, the prefix and the reference names, and fit them all in 2,000 characters.
    • 
            
  • Keep the context in the messages, not only the prompt. The prompt is fixed at the first question; a prefix on every message keeps later answers current, and makes the transcript readable for your team.
    • 
            
  • Make references a closed list with a few aliases. The Stand-in sometimes writes [[Tap reader]] instead of [[Checklist: Point of sale]]; an alias turns the near miss into a working chip.
