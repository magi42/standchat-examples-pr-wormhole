Basalt is a fictional company. This page demonstrates a custom chat UI on Stand Chat's Visitor API: the playground is real Postgres in your browser, and the conversations are real.

How it works

Put the conversation where developers get stuck: inside the sandbox

A developer product's moment of truth is the first query that fails. Here the playground is real Postgres running in the browser, and the question box sits beside the error. One click sends the question to the team with everything they'd otherwise have to ask for: the query, who it ran as, and what Postgres said. SQL in the answer runs back in the same sandbox, and only when the visitor clicks.

There's no stand.js on this page. The conversation runs on Stand's Visitor API (beta) through stand-visitor.js, and the database is PGlite, Postgres compiled to WebAssembly, loaded from a CDN when the playground comes into view.

Try it

  1. The playground opens on a failing insert: Cy, a member of Globex, can't log an invoice. Click Ask why this failed. The question goes out with the query, the role and the error attached.
  2. Follow up, for example "How would I let any member create invoices?" When the answer has SQL, click Run in playground. Schema changes run as service_role; everything else runs as the user in "Run as".
  3. Run Cy's insert again. Click a policy or table name in an answer to see it in the dashboard.
  4. Change "Run as" and watch the row counts under Tables move, or switch a policy off under Policies. Then reload: the conversation, your query and the database's changes all come back.
This example uses site: 'demo', Stand Chat's shared demo site, which works on any domain. Its demo Stand-in answers as Basalt from the facts in the page's prompt. With your own Site ID, your own Stand-ins answer with your knowledge and skills, and your team can take over.

1. Real Postgres, with roles and claims

PGlite runs in a worker, so a 5 MB download and a slow query never freeze the page. The seed creates a tiny multi-tenant app (organizations, members, projects, invoices, profiles), three roles, and row-level security policies that read the signed-in user from JWT claims, the way a hosted API would:

create function auth.uid() returns uuid language sql stable as $$
  select nullif(auth.jwt() ->> 'sub', '')::uuid
$$;

alter table invoices enable row level security;
create policy "admins read invoices" on invoices for select
  to authenticated using (is_admin(org_id));
create policy "admins create invoices" on invoices for insert
  to authenticated with check (is_admin(org_id));

"Run as" turns each run into an API request in miniature: set the role, set the claims, run, then reset so the next run starts clean.

await db.exec(`set role ${role}; select set_config('request.jwt.claims', ${literal(JSON.stringify(claims))}, false);`);
const results = await db.exec(sql, { rowMode: 'array' });
// Then: roll back anything left open, and reset the role and the claims.

2. The context travels with the question

Every question starts with a short prefix: who ran the query and what Postgres answered, with the SQL on the next lines. The team reads exactly this in Stand, and after a reload the page reads it back from the transcript to draw the chips, so nothing else needs storing:

[as Cy · ERROR 42501: new row violates row-level security policy for table "invoices"] Why did this fail?
```sql
insert into invoices (org_id, project_id, number, amount_cents, due_on)
values (2, 4, 'GX-2003', 480000, '2026-10-31');
```

Here is what your next question would carry, updated as you use the playground above:

[as Cy · ERROR 42501: new row violates row-level security policy for table "invoices"] Your question goes here.

Sending is one call. The first message also carries the private prompt for whoever answers:

const body = composeMessage(question, playground.contextFor(result));
await client.send(body, { prompt: PROMPT, analyticsId: 'playground-error' });

3. The prompt

Private context for the AI Stand-in and your team, 1,980 of Stand's 2,000 characters: the facts to answer from, the schema and policies, the message format, and the names a reply may point at. It's in the page's source, so it holds nothing secret.

You are answering visitors on the website of Basalt, a fictional hosted Postgres platform (a demo on examples.stand.chat; Basalt is invented). Speak as Basalt's team. Reply in 1-3 sentences unless asked more. If a fact isn't below, say you're not sure and offer to bring in someone from the team. Don't invent prices, limits or features.

Messages start with [as <user> · <result>], then the question and maybe SQL. When SQL helps, write complete, valid Postgres in a ```sql block (to change a policy, drop and recreate it): the visitor can run it with one click. Cite the deciding policy or table by exact name, as [[policy: name]] or [[table: name]], at most two.

4. Answers you can run, and point at

Replies are text. The page escapes them and allows a small safe subset: paragraphs, lists, bold, inline code, links, fenced code. A ```sql block becomes a block with Run in playground and Copy. Nothing in a reply ever runs by itself:

  • A click runs the SQL in this tab's database only, as the user in "Run as". Statements that change the schema run as service_role, and the block says so before you click.
  • The result appears under the block: rows, INSERT 1, or an error with its own Ask why.
  • Postgres can't be interrupted inside WebAssembly, so Stop restarts the worker and replays your earlier changes. Reset goes back to the seed.

Names in double brackets, like [[policy: admins read invoices]], become chips that open the policy or table and highlight it. The prompt lists the exact names; the page compares them without case or stray punctuation, and anything it doesn't know stays plain text.

if (node.type === 'ref') {
  const ref = playground.resolve(node.raw); // tables and policies that exist right now
  return ref ? refChip(ref.kind, ref.name) : node.raw.replace(/^\s*(table|policy)\s*:\s*/i, '');
}

5. What the team learns

Every question arrives in Stand with the role, the error code and the SQL. After a week, the team knows which errors and which policies confuse people, in their own words: the insert that violates a policy, the empty result nobody expected, the grant that isn't a policy. That's the docs page to write next, the error message to improve, the default to change. The analytics ID on the first message tells them which button started the conversation: the error panel, an empty result, a policy card or the composer.

The files

  • stand-visitor.js is the part to copy: discovery, one-time creation, idempotent sends, WebSocket receive, recovery, handoffs and follow-ups, with no DOM.
  • context.js is the conversation model: the prompt, and the message prefix written and read back. format.js turns replies into a safe tree.
  • assistant.js draws the conversation, the attached context, runnable SQL and reference chips, and the phone's bottom sheet.
  • playground.js is the dashboard: views, "Run as", results, tables, policies, users, and the change journal. sql-editor.js and sql.js are the editor and a small SQL tokenizer.
  • db.js and db-worker.js run PGlite in a worker, with download progress and Stop. sandbox.js is the sample app: seed, users, policies and snippets.

Good to know

  • Honest about who answers. The panel shows the responder's name as Stand gives it, with AI Stand-in or Team member. When someone from the team takes over, a note says so and the label changes.
  • One click, one conversation. The first question starts the chat; loading the page, opening the panel or attaching a query never does. Later questions join the same conversation.
  • Closing isn't ending. On phones the sheet closes and the conversation carries on. Only End conversation ends it in Stand.
  • A reload keeps everything. The transcript comes from Stand; the query, role and view from sessionStorage. Postgres lives in memory, so it starts fresh and replays a journal of your changes. Without storage, it all still works and forgets on reload.
  • Nobody around, nothing lost. If nobody can answer, the ask buttons say so, and the question waits in the box with its query attached.
  • Heavy parts load late. Postgres is about 5 MB compressed. It downloads when the playground comes into view or someone touches it, with real progress, while the page shows the example's recorded result.
  • Keyboard and screen readers. The views are tabs, "Run as" is a listbox, ⌘/Ctrl + Enter runs, and Esc then Tab leaves the editor. Replies are announced whole. Reduced motion turns off the pulses and slides.
  • It's a beta. The Visitor API can grow new fields and events. The client ignores what it doesn't know.

This example's brief

A SQL playground that answers back. An invented hosted-Postgres platform, in the dark, green look of a well-known open-source backend built on Postgres, runs real Postgres in the browser on its homepage: PGlite, a tiny multi-tenant schema, row-level security policies and a role switcher. Visitors run queries as different users and watch rows appear and vanish. When a query errors or surprises them, one click asks the team with the query, role, error and policies attached, in an assistant panel on the right. SQL in the answer runs in the local sandbox with one click, never automatically, and [[references]] highlight tables and policies. On phones the playground stacks and the assistant becomes a bottom sheet.

If you try this yourself

  • Link the custom chat UI guide and start on the demo Site ID, so the agent holds real conversations while it builds.
  • Put the schema, the users and the policy names in the prompt, and say the visitor can run the SQL. The Stand-in then writes statements against the real tables. One more line, "to change a policy, drop and recreate it", ended its invalid ALTER POLICY attempts.
  • Group the policies by command in the prompt, and show the reference format with a placeholder, like [[policy: name]]. With a real policy as the example, the Stand-in kept citing that one, even for inserts. On the page side, accept names without case or stray punctuation, even in backticks, which the demo Stand-in likes to add.
  • Test the rare states with a fake Stand: intercept the API in headless Chrome and swap in a fake WebSocket, and handoffs, email offers and failed sends render without a single real chat.
