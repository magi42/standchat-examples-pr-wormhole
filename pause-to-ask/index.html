    Marquee is a fictional company. This page demonstrates a custom chat UI on Stand Chat’s Visitor API.

    How it works

    Let visitors pause your demo and ask about what they see

    Every product has a demo video, and nobody knows where viewers get lost. Here the tour is a live animation you can pause at any second. A question carries the moment it’s about, drops onto the timeline as a marker, and the answer can jump the tour to the moment it means. It’s a custom chat UI on Stand’s Visitor API: one real conversation, answered by an AI Stand-in, with your team a click away.

    Try it

    1. Let the tour play, or drag along its chapters. Hover the timeline to preview any second.
    2. Pause when something catches your eye and choose Ask about this moment, or press Q. Try “If I shrink this headline, does desktop change too?” at 0:42.
    3. Your question drops onto the timeline as a marker, and the answer arrives in the Questions rail. Times in it, like 0:39, play the tour from there.
    4. Ask about another moment: it gets its own marker and thread. Then reload the page. The markers, the threads and the frame you were on all come back.
    This page uses site: 'demo', Stand Chat’s shared demo site, which works on any domain. Its demo Stand-in follows the page’s prompt, but won’t speak for the made-up business. With your own Site ID, your own Stand-ins answer, and your team can step in.

    1. The tour is a function of time

    There’s no video file. The editor is HTML and CSS, laid out at a fixed size and scaled like a video. render(t) sets every element from a script: where the cursor is, how much of the headline is typed, which menu is open, how far the canvas has zoomed. Nothing animates on its own, so seeking is instant, a paused frame stays exactly still, and any second can be drawn again, which is what a question needs to point at.

    // What happens when, in seconds. The cursor aims at elements, not pixels,
// so the same script drives the desktop layout and the compact phone one.
go(39.4, 'p:headline@0.5,0.5', 1.2); // arrive on the phone's headline
click(39.6);
go(41.6, 'insp-size@0.22,0.5', 0.8); // drag the size field: 44 → 36
export const AT = { phoneSize: [40.8, 41.6], locale: 85.9 };
    function render(t) {
  renderSite(t);     // the site being built: typed text, swapped image, French copy
  renderChrome(t);   // panels, layers, inspector values
  renderOverlays(t); // template gallery, CMS, menus, preview, the live site
  renderWorld(t);    // where the canvas looks, and how close
  renderCursor(t);   // eased moves between targets, clicks as ripples
}
player.seek(72); // → tour.render(72), and the scrubber, captions and markers follow

    The previews work the same way. Hover the timeline, a marker or a time in an answer, and a second, smaller copy of the tour renders that exact second.

    2. A question carries its moment

    Pausing gives the question its context: the second, the chapter and what’s on screen. Every visitor message starts with that moment, so your team reads exactly where the question came from, and the page can read it back.

    formatQuestion(42, 'Does desktop change too?');
// → "⏱ 0:42 Breakpoints: Does desktop change too?"

parseQuestion('⏱ 0:42 Breakpoints: Does desktop change too?');
// → { time: 42, text: 'Does desktop change too?' }

    Paused at 0:40, Breakpoints, your next question would be sent as:

    ⏱ 0:40 Breakpoints: Your question

    3. Markers are threads in one conversation

    Each moment gets its own marker and thread, but they all live in one Stand conversation, so a visit counts as one chat however many questions it raises. The threads are rebuilt from the transcript: a reply belongs to the thread of the latest question before it. After a reload, the markers come back from the messages themselves.

    const { threads, notices, awaiting } = buildThreads(client.getSnapshot());
// threads: one per moment, in timeline order, each with its messages.
// notices: handoffs, follow-up offers and the end, for the whole conversation.
// awaiting: the thread an answer is due in. Other moments wait their turn.
player.setMarkers(threads.map((t) => ({ key: t.key, time: t.time, kind: 'you' })));

    4. Answers that seek

    The prompt lists the chapters and what’s on screen every few seconds, and asks the Stand-in to point at moments in double brackets. It does, reliably. The page turns those into timestamp chips that play the tour from there. It’s a closed vocabulary: anything else in brackets is shown as plain text, and a reply can only ever move the tour.

    resolveReference('0:39');         // → { kind: 'time', time: 39, label: '0:39' }
resolveReference('Chapter: CMS'); // → { kind: 'chapter', time: 48, label: 'CMS' }
resolveReference('Pricing');      // → null: shown as plain text

    What your team learns

    Analytics can tell you that people stop watching at 0:40. Here they tell you why. Every question arrives in Stand with the second it was asked, so your team sees which part of the demo raises questions, what those questions are, and how the answer went. When the same moment keeps coming up, that’s a feature to explain better, or to rethink.

    Good to know

    • Honest about who answers. The rail shows the responder’s name exactly as Stand gives it, and whether it’s an AI or a person. The example threads you see before your first question are marked as examples, and their answers aren’t attributed to anyone.
    • One chat per visit. Every marker is a thread in the same conversation. While an answer is due, other moments wait for it, so replies never land in the wrong thread.
    • Closing isn’t ending. Closing the question box, or pressing Esc, keeps everything. Only End conversation, at the bottom of the rail, closes it in Stand.
    • A reload keeps everything. The client restores the conversation from sessionStorage and Stand, the markers come from the transcript, and the tour’s position and open thread are saved under the example’s own key. Without storage, it still works; it just forgets on reload.
    • When nobody can answer, the Ask buttons still open, say so, and offer to try again. Nothing is created until a question is sent.
    • Keyboard and screen readers. Space or K plays and pauses, J and L skip, the arrow keys step through the timeline, and Q asks. Captions narrate the tour, the whole tour is also available as text, and answers are announced as they arrive.
    • Reduced motion. The tour doesn’t autoplay; it waits on a still frame. When played, it skips the zooms.
    • It’s a beta. The Visitor API can grow new fields and events. The client ignores what it doesn’t know, and a custom UI keeps Stand’s notices and attribution.
    How this was made

    Claude Opus 5.5 in Claude Code built this example from a brief. A lead session reworked a list of ideas for custom chat UIs, wrote the brief below and reviewed the result. A separate Claude agent built the page in its own git worktree: it studied a well-known website builder’s site for tone, scripted the tour second by second, tuned the prompt in real conversations with Stand’s demo Stand-in until the timestamps it cited matched the screen, and checked its own screenshots in headless Chrome at desktop and phone sizes.

    The prompt, lightly edited

    Given Stand Chat's target audience, find ten products they look up to and would recognize, products that might have the same problems as their own. It could be the market's dominant player. For each, work out how it could embed Stand on its website in an innovative way that pulls visitors in to interact. Not just a chat button, but something novel: something our audience would see and think, "I want that on MY website." Build each one in a separate session, as its own pull request. Don't use the brand names, but make each website resemble its product in a subtle way.

    This example’s brief

    Marquee, a made-up website builder with a bold black marketing site, has a product tour you can pause at any moment to ask about exactly what’s on screen. The tour is not a video file: it’s a live, seekable animation of the editor building a site, drawn by render(t) so seeking is instant. Chapters: Templates, Canvas, Breakpoints, CMS, Effects, Localization, Publish. The player has play and pause, a chapter scrubber, captions, keyboard shortcuts and "Ask about this moment" (Q). A question carries its timestamp, drops a marker on the timeline, and lives in a Questions rail synced with playback. Answers point at times like [[1:12]], rendered as chips that seek the tour. All markers are threads in one Stand conversation, rebuilt from the transcript after a reload.

    If you try this yourself

    • Link the custom chat UI guide. It’s written as a contract for coding agents.
    • Start on the demo Site ID, so the agent can hold real conversations while it builds, then switch to yours.
    • Generate the prompt’s outline from the same data that drives your demo. The Stand-in cites times precisely when every moment it knows is one it can see.
    • Make the demo a pure function of time and have the agent screenshot chosen seconds. Each frame is a test it can look at and fix.
