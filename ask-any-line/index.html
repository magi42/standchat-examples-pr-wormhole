1

Set up Tender

Install the library

Add Tender's server library. It signs every request with your key, retries safely when the network drops, and checks webhook signatures for you.

curl talks to the API directly, so the calls need nothing installed. For webhooks, get the Tender CLI: it forwards events to your machine and sends test ones.

Terminal

Server

Add your API keys

Your account has two pairs of keys. The secret key, tk_test_…, stays on your server in an environment variable, never in your repository. The publishable key, tpub_test_…, is safe to ship to the browser.

Pin the API version as well. Your integration keeps behaving the same way when Tender ships changes, until you upgrade on purpose.

.envTENDER_SECRET_KEY=tk_test_4Qa8Lm2Zx7Rc…
TENDER_WEBHOOK_SECRET=tws_test_…

2

Create a payment

Add an endpoint

Your checkout page calls this endpoint when the customer is ready to pay. Create one payment per order: it follows the attempt from the first try to the final result, retries and declines included.

Server

Set the amount

Amounts are integers in the currency's smallest unit, so 2000 is $20.00. Work out the total on your server from the order, and never trust a price the browser sends you.

With automatic payment methods, Tender offers every method you've enabled in the dashboard that fits the currency and the customer's country.

Server

Make it safe to retry

Send an idempotency key with the request, such as the order ID. If a request times out and you send it again, Tender returns the payment it already created instead of charging twice. Keys expire after 24 hours.

Server

Return the client secret

The new payment has a client_secret. Send only that to the browser: it lets Tender.js confirm this one payment and nothing else. Don't log it, and keep it out of URLs.

Server

Collect card details

Load Tender.js

Load Tender.js from js.tender.dev instead of bundling it, so card numbers go straight to Tender and never touch your servers. Then create an instance with your publishable key.

<form id="payment-form">
  <div id="card-field"></div>
  <button>Pay $20.00</button>
</form>
<script type="module" src="checkout.js"></script>

Browser

Mount the card field

Fetch the client secret from your endpoint, then mount the card field into your form. It's a secure iframe that validates as the customer types and picks up your page's font.

Browser

Confirm the payment

When the customer clicks Pay, call confirmPayment. If the bank asks for 3-D Secure, Tender.js shows the challenge and carries on by itself. On success, the customer lands on your returnUrl.

Show error.message as it is. It's written for customers, like “Your card was declined.”

Browser

4

Handle webhooks

Verify the signature

Tender sends a payment.succeeded event to your webhook endpoint when the money is in. Before you trust it, check the Tender-Signature header with your endpoint's secret.

Verify the raw request body. Parsing the JSON first changes the bytes, and the signature won't match.

Server

Fulfill the order

Fulfill from the webhook, not from the return page. A customer can close the tab before the redirect finishes, but the event always arrives.

Server

Reply right away

Reply with a 2xx within 10 seconds, then do slow work, like emailing the receipt, in the background. Tender retries failed deliveries with backoff for up to three days.

Tender is a fictional company. This page demonstrates a custom chat UI on Stand Chat's Visitor API: questions go to a real conversation, answered by Stand's demo AI Stand-in.

How it works

Let developers ask about the exact line that confused them

Docs are where a developer tool wins or loses its users, and the questions that decide it are small: why 2000 and not 20, which header, what happens on a retry. On this quickstart, a developer can ask about any line of code or any sentence. The answer lands right there, as an annotation under the line, like a comment in a code review. Every question reaches the team through Stand with its file, line and language, so the team learns exactly which line of the quickstart trips people up.

There's no stand.js on this page. The annotations are plain JavaScript in this folder, on Stand's Visitor API, and every thread you open is part of one real conversation.

Try it

  1. Hover a line in the code panel and click +. With a keyboard, tab into the code, move with ↑ ↓ and press Enter. Ask something small, like “Why 2000 and not 20?”
  2. Switch from Node to Python. Your question and its answer move to the matching Python line.
  3. Select a sentence in the guide and choose Ask about this, or use Ask about this step next to a step's title.
  4. When an answer names another part of the code, click it: the code panel jumps there and lights it up.
  5. Reload mid-conversation. Every thread comes back where it was. End conversation is at the bottom of the code panel.
Questions here use site: 'demo', Stand Chat's shared demo site, which works on any domain. Its demo Stand-in answers from this page's prompt, as the made-up Tender team. With your own Site ID, your own Stand-ins answer, and your team can take over from Stand.

1. Every line has a logical ID

The samples live in the page as plain text, one line per row, with an ID that says what the line does. The same statement has the same ID in every language, so a thread asked on Node's amount: 2000, knows that Python's amount=2000, is the same line.

<script type="text/plain" data-sample="server" data-lang="node" data-file="server.js">
create-payment │   const payment = await tender.payments.create(
params-open    │     {
amount         │       amount: 2000, // $20.00, in cents
currency       │       currency: 'usd',
</script>

<script type="text/plain" data-sample="server" data-lang="python" data-file="server.py">
create-payment │     payment = client.payments.create(
amount         │         amount=2000,  # $20.00, in cents
currency       │         currency="usd",
</script>

Python has no line for the opening {, so catalog.js lists where such a line's thread goes instead: params-open falls back to create-payment. curl has no web server at all, and its lines answer to a few IDs at once. When you switch languages, each annotation looks up its line in the new sample and slides there.

// Where a code thread sits: the exact line it was asked on, in that language.
// In any other language, the same statement, found by its logical ID.
function lineFor(anchor) {
  if (anchor.file === 'client' || anchor.lang === ui.lang) return anchor.n;
  const from = catalog.file(anchor.file, anchor.lang)?.lines[anchor.n - 1];
  return lineOf(anchor.file, partLine(anchor.part) ?? from?.id);
}

// catalog.js: follow the fallbacks until the language has the line.
locate(kind, lang, id) {
  for (let at = id; at; at = FALLBACK[at]) {
    const line = this.file(kind, lang).lines.find((l) => l.ids.includes(at));
    if (line) return { line, exact: at === id };
  }
}

2. One conversation, many threads

The threads aren't separate chats. Every Stand session counts against the site's chats, and whoever answers is better off with one conversation per visitor. So every question starts with where it was asked, readable at a glance in Stand:

⌘ server.py L20 (Python) — amount: Why 2000 and not 20?
⌘ checkout.js L12 (browser) — mount card field: Can I style the field?
¶ Step 4 “Handle webhooks”: “Reply with a 2xx within 10 seconds” — Even for events I ignore?
¶ Step 5 “Test it”: How do I test a refund?
§ Accept a payment: Do you support Apple Pay?

The prefix is also how the page finds each message's thread again after a reload: it parses the transcript, so the threads need no storage of their own. A reply belongs to the thread of the latest question before it. While an answer is on its way, asking on another line waits for it, so answers can't land in the wrong place.

const LINE = /^⌘ (\S+) L(\d+) \(([^)]*)\) — (.+?): ([\s\S]*)$/;

for (const m of state.messages) {
  if (!isConversation(m)) continue; // cards, and our own prompt echoed back
  if (m.senderType === 'visitor') {
    const parsed = parseMessage(m.body, catalog); // { anchor, question }
    const thread = ensure(parsed.anchor); // "line:server:amount", "step:4", …
    thread.items.push({ kind: 'visitor', m, question: parsed.question });
    current = thread.key;
  } else {
    threads.get(current).items.push({ kind: 'reply', m, author });
  }
}

3. The prompt

The first question carries a private prompt for whoever answers: the AI Stand-in, and anyone on your team reading the conversation in Stand. It stays under Stand's 2,000 characters, and ends with where the visitor was. Here it is, live: until you ask something, its last line follows you around the page. After that, it's the prompt your conversation started with, as Stand echoes it back.



      
4. Answers that point at lines

      
The prompt lists the page's parts by name and asks for at most two references per answer, in double brackets. In testing, the demo Stand-in writes them like nouns: “the client secret comes back from [[create payment]]”. Each known name becomes a chip that shows where that part is in your language. A click switches to the right file, scrolls, and lights up the whole statement. Unknown names stay plain text, and a person on the team never has to use them.

      
// cards.js hands every [[name]] in an answer to this.
function chip(name) {
  // "create payment" → { kind: 'code', file: 'server', id: 'create-payment' }
  const target = resolveReference(name);
  if (!target) return null; // plain text, without the brackets
  const button = el('button', 'ref');
  const at = lineOf(target.file, target.id); // in the language on screen
  button.append(name, ` ${fileName(target.file)}:${at}`);
  // A click switches file, scrolls and flashes the lines. Never more.
  button.addEventListener('click', () => goTo(target));
  return button;
}


      
5. Ask about a sentence

      
Selecting text in the guide shows Ask about this by the selection (below it on touch screens, where the system's own menu sits above), or press ? after selecting with the keyboard. The thread opens under the paragraph and quotes what you selected. On very wide screens it sits in the margin beside the paragraph instead, next to labels that say which lines each part of the guide is about. After a reload, the page finds the paragraph again by searching the step for the quote, and highlights the sentence with the CSS Custom Highlight API, without touching the text.

Good to know

      
    
        
  • Honest about AI. Every answer shows the name Stand gives its author and an AI badge for a Stand-in. If someone from the team takes over, their answers say Team, and the code panel says who joined.
    • 
        
  • Resolving isn't ending. Resolve folds a thread into a check mark in the gutter. The conversation goes on until you choose End conversation at the bottom of the code panel, which closes it in Stand.
    • 
        
  • A reload keeps everything. Threads come back from the transcript, in their places and in your language. The language, resolved threads and an unsent question are kept in sessionStorage. Without storage, it all still works until the tab closes.
    • 
        
  • Nobody around? If Stand finds no one who can answer, the ask boxes say so and offer to check again, instead of taking a question nobody will read.
    • 
        
  • Keyboard and screen readers. Skip to the code is the first stop. Every line is reachable with the arrow keys, Enter or ? asks about it, Esc closes a box and returns focus to the line, and / jumps to search. Whole answers are announced as they arrive, never letter by letter.
    • 
        
  • Reduced motion. The header's gradient stops, and annotations appear in place instead of sliding.
    • 
        
  • It's a beta. The Visitor API can grow new fields and events. The client ignores what it doesn't know.

This example's brief

          
Docs for an invented payments API, in the three-column look of the payments docs every developer-tools founder imitates: navigation, prose steps, and a sticky dark code panel with file and language tabs.
Let developers ask about any line: a + in the gutter opens a question box under the line, and the answer arrives there as an annotation, like a code-review comment.
Selecting a sentence offers "Ask about this"; the thread opens as a note by the paragraph.
Give every line a logical ID shared across Node, Python, Ruby, Go and curl, so switching languages keeps each annotation on the matching line.
Replies point at lines with references that become chips; clicking one scrolls to the line and flashes it.
All threads are one Stand conversation, with a readable prefix per message. The team learns which line, in which language, confuses people.


          
If you try this yourself

          
    
            
  • Start from the custom chat UI guide, which is written as a contract for coding agents, and on the demo Site ID, so the agent can hold real conversations while it builds.
    • 
            
  • Put the anchor in the message, not in storage. A prefix like ⌘ server.py L20 (Python) — amount: tells the team where the question was asked and tells the page where to put it back.
    • 
            
  • References became reliable once the prompt showed one in use (like [[verify signature]]) and listed the names. Without the example, the Stand-in never used them.
    • 
            
  • Handoffs, email follow-ups and link cards never happen on the demo site. Test them against a small fake of Stand's API that your test script injects into the page, so the real client and UI run unchanged.
